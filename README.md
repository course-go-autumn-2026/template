# TripGo — лабораторная работа 1

HTTP API поездок на `net/http` и `chi`, PostgreSQL через `pgxpool`, SQL через
`squirrel`. Создание и завершение поездки записывают историю статуса в одной
транзакции с изменением поездки.

## Требования

- Go 1.26.2 (версия указана в `go.mod`).
- Docker и установленный `tripgoctl` из
  [course-infra](https://github.com/course-go-autumn-2026/course-infra).
- Для примеров запросов — `curl`, для извлечения ID — `jq`.

Версии `goose` и `oapi-codegen` закреплены в `go.mod`; инструменты запускаются
через `go tool`.

## Запуск из клона

В корне репозитория:

```sh
go mod download
tripgoctl cluster start
tripgoctl environment start
tripgoctl connect
```

Кластер создаётся один раз. `environment.toml` выбирает окружение ЛР1 с PostgreSQL.
`tripgoctl` создаёт `.env` с адресом БД. Сохраните сгенерированный `DATABASE_URL`
и добавьте в `.env` недостающие переменные из `.env.example` по таблице ниже.
Демонстрационный `DATABASE_URL` из `.env.example` не заменяет адрес окружения.

```sh
make generate
make build
make migrate-up
make migrate-status
make run
```

`make run` экспортирует переменные из `.env`. На старте проверяется конфигурация
и выполняется `Ping` PostgreSQL. При ошибке сервис завершается с сообщением.
`Ctrl+C` запускает graceful shutdown; поддерживается и `SIGTERM`.

## Переменные окружения

Все переменные обязательны. Таймауты и время жизни соединений должны быть
положительными; длительности задаются в формате Go, например `3s` или `30m`.
Конфигурация читается из env через `cleanenv`; ограничения значений заданы
тегами `validator`. Уровень логирования принимается без учёта регистра.

| Переменная | Значение в примере | Назначение |
|---|---|---|
| `HTTP_ADDR` | `:8080` | Адрес HTTP-сервера |
| `HTTP_READ_TIMEOUT` | `10s` | Чтение запроса |
| `HTTP_READ_HEADER_TIMEOUT` | `5s` | Чтение заголовков |
| `HTTP_WRITE_TIMEOUT` | `10s` | Запись ответа |
| `HTTP_IDLE_TIMEOUT` | `60s` | Ожидание следующего запроса |
| `LOG_LEVEL` | `info` | Проверяется при старте; настройка `slog` предусмотрена в ЛР2 |
| `SHUTDOWN_TIMEOUT` | `10s` | Общий бюджет остановки HTTP-сервера и пула |
| `DATABASE_URL` | из `.env`, созданного `tripgoctl` | Подключение к PostgreSQL |
| `DATABASE_MAX_CONNS` | `10` | Максимум соединений, больше нуля |
| `DATABASE_MIN_CONNS` | `2` | Минимум соединений, от нуля до максимума |
| `DATABASE_MAX_CONN_LIFETIME` | `30m` | Время жизни соединения |
| `DATABASE_CONNECT_TIMEOUT` | `5s` | Подключение к БД |
| `DATABASE_QUERY_TIMEOUT` | `3s` | Запрос к БД и проверки доступности |

`.env` и `.tripgo/` исключены из git. Адреса и учётные данные БД в коде отсутствуют.

## HTTP API

| Метод | Путь | Результат |
|---|---|---|
| `POST` | `/api/v1/trips` | `201`, поездка и заголовок `Location` |
| `GET` | `/api/v1/trips/{tripId}` | `200`, поездка |
| `POST` | `/api/v1/trips/{tripId}/finish` | `200`, завершённая поездка; тело запроса пустое |
| `GET` | `/health` | `200`, процесс работает; обращений к БД нет |
| `GET` | `/ready` | `200` при доступной БД, иначе `503` |

Успешные ответы и обе служебные ручки возвращают `application/json`.
Ошибки бизнес-ручек — `application/problem+json` с полями `type`, `title`,
`status`, `detail`, `instance`, `code`:

- `400 invalid_request` — неверный JSON, UUID, отсутствующие или неизвестные
  поля, `null`, недопустимые координаты или отрицательная цена;
- `404 trip_not_found` — поездки нет;
- `409 driver_busy` — у водителя уже есть активная поездка;
- `409 trip_completed` — повторное завершение;
- `500 internal_error` — внутренняя ошибка, подробности доступны в логе.

### Пример запросов

В другом терминале загрузите `.env` и выберите адрес HTTP-сервера:

```sh
. ./.env
case "$HTTP_ADDR" in
  :*) BASE_URL="http://localhost$HTTP_ADDR" ;;
  *) BASE_URL="http://$HTTP_ADDR" ;;
esac

curl -i "$BASE_URL/health"
curl -i "$BASE_URL/ready"

TRIP_ID=$(curl -fsS -X POST "$BASE_URL/api/v1/trips" \
  -H 'Content-Type: application/json' \
  -d '{"user_id":"5cb72c04-7650-45c9-a79b-bcdba0631e0c",
       "driver_id":"8860b315-ec86-42eb-a17c-7c163d721ff5",
       "start_point":{"latitude":59.9398,"longitude":30.3146},
       "end_point":{"latitude":59.9290,"longitude":30.3626},
       "price":1450}' | jq -r '.id')

curl -i "$BASE_URL/api/v1/trips/$TRIP_ID"
curl -i -X POST "$BASE_URL/api/v1/trips/$TRIP_ID/finish"
curl -i -X POST "$BASE_URL/api/v1/trips/$TRIP_ID/finish"
```

Последний запрос возвращает `409 trip_completed`. Повторное создание на того же
водителя до завершения первой поездки возвращает `409 driver_busy`.

## Команды и проверка

```sh
make build                          # go build ./...
make test                           # go test -race ./...
make generate                       # пять операций OpenAPI для ЛР1
make migrate                        # то же, что migrate-up
make migrate-up
make migrate-status
make migration-create NAME=change   # новая последовательная SQL-миграция
make connect
```

`make migrate-down` откатывает одну миграцию. На отдельной тестовой БД можно
проверить полный цикл: два вызова `make migrate-down`, затем `make migrate-up`.
Откат удаляет таблицы с данными. Применённые миграции не редактируются.

Для проверки `/ready` оставьте сервис запущенным: после `tripgoctl environment
stop` ожидается `503`, после `tripgoctl environment start` и восстановления
подключения — `200`. `/health` продолжает отвечать `200`.

Проверьте также 20 параллельных созданий на одного свободного водителя: ожидается
один `201` и 19 ответов `409 driver_busy`. Для 20 параллельных завершений одной
активной поездки ожидается один `200` и 19 ответов `409 trip_completed`.
В истории этой поездки должны остаться ровно две записи: создание и завершение.

Автоматические тесты в рамках ЛР1 не добавлены; `make test` выполняет проверку
существующих пакетов с `-race`. Требования к набору тестов вводятся в ЛР2.

## Структура

- `cmd/trip-service/` — запуск и сборка зависимостей;
- `internal/app/` — HTTP-ручки, функции `validate...` под соответствующими
  ручками, преобразование моделей и ошибок;
- `internal/service/` — создание, получение, завершение, запись истории
  и проверка готовности через `checkup`;
- `internal/domain/` — модели, ошибки, интерфейсы и реализации репозиториев;
- `internal/postgres/` — пул, выбор исполнителя и менеджер транзакций;
- `internal/config/` — чтение и проверка env;
- `internal/generated/` — код OpenAPI, как в примере ЛР1;
- `contracts/` — исходные контракты курса;
- `migrations/` — миграции `goose`.

В conventions указан каталог `api/`; здесь выбран `internal/generated/` из
команды генерации в ЛР1. `make generate` воспроизводит этот результат.

## Решения

- HTTP-типам источником служит OpenAPI. Сгенерированные файлы не правятся вручную.
  `validateCreateTripRequest` разбирает JSON и проверяет данные через ozzo.
  Наличие обязательных JSON-полей проверяется отдельно от их значений, поскольку
  сгенерированные `int64` и `float64` не различают отсутствие поля и допустимый
  ноль. Неизвестные поля запрещены, в теле разрешён один JSON-объект.
- Репозитории получают пул и таймаут через конструктор. SQL собирается
  `squirrel` с параметрами `$N`. Каждый запрос ограничен таймаутом и использует
  контекст входящего запроса.
- `/ready` вызывает сервис `checkup`, который проверяет БД через `Ping`
  с `DATABASE_QUERY_TIMEOUT` и контекстом запроса. HTTP-слой преобразует результат
  в `200` или `503` со схемой `HealthResponse`.
- `TxManager.Do` открывает транзакцию и сохраняет её в контексте. Репозитории
  выбирают её из контекста, а вне `Do` используют пул. Вложенный `Do`
  переиспользует транзакцию. Успех приводит к `COMMIT`, ошибка или паника — к
  `ROLLBACK`; паника распространяется наружу. Откат имеет отдельный таймаут и
  выполняется даже при отмене исходного контекста.
- Изоляция — `READ COMMITTED`. Уникальный частичный индекс
  `trips_active_driver_uidx` запрещает две активные поездки одному водителю.
  Конфликт индекса распознаётся по `23505` и имени ограничения.
- Завершение выполняется условным `UPDATE ... WHERE status = 'active' RETURNING`.
  Это защищает от двойного завершения. Если строка не обновилась, дополнительный
  `SELECT` в той же транзакции различает отсутствие поездки и повторный вызов.
  Повторное завершение не меняет `finished_at`.
- Создание и завершение вызывают запись поездки и истории внутри одного `Do`.
  История дополняется новой записью на каждый переход: `NULL → active`, затем
  `active → completed`. Ошибка записи истории откатывает изменение поездки.
- По сигналу HTTP-сервер перестаёт принимать запросы, дожидается текущих, затем
  закрывается пул БД. Всё ограничено общим `SHUTDOWN_TIMEOUT`.
