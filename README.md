# Trip service

HTTP-сервис лабораторной работы №1: создаёт, возвращает и завершает поездки,
хранит данные в PostgreSQL и поддерживает идемпотентное создание поездки.

## Локальный запуск

Нужны Go 1.26, GNU Make, `tripgoctl` и запущенный кластер курса.

```bash
tripgoctl cluster start
tripgoctl environment start
tripgoctl connect
make migrate
make run
```

Проверка готовности: `curl -i localhost:8080/ready`.

Основные команды: `make migrate`, `make migrate-down`, `make generate`,
`make build`, `make run`.

## Архитектура

Проект построен по слоистой архитектуре с изоляцией домена и соблюдением принципа инверсии зависимостей (Dependency Inversion):

1. **Доменный слой (`internal/domain`)**:
   - Содержит бизнес-сущность `Trip`, статусы и методы переходов (`Finish(time.Time)`).
   - Инкапсулирует доменные ошибки (`ErrTripNotFound`, `ErrTripCompleted`, `ErrDriverBusy`, `ErrInvalidRequest`, `ErrIdempotencyConflict`, `ValidationError`).
   - Полностью изолирован от внешних инфраструктурных пакетов (`net/http`, `pgx`, `chi` и т.д.).

2. **Слой бизнес-логики / сценариев (`internal/usecase`)**:
   - Организован по паттерну «package per action»: `create`, `get`, `finish`.
   - Определяет интерфейсы потребителя (consumer-defined interfaces) для доступа к данным (`tripRepository`, `tripHistoryRepository`, `txManager`, `metricsRecorder`).
   - Управляет выполнением бизнес-правил, вызовом метрик и фиксацией транзакций.

3. **Слой репозиториев (`internal/repository`)**:
   - Реализует хранение данных в PostgreSQL (`trip`, `idempotency`).
   - Использует `pgxpool` и построитель запросов `squirrel`.
   - Поддерживает прозрачную работу с транзакциями через `TxFromContext(ctx)`.

4. **HTTP-транспорт (`internal/http`)**:
   - Хендлеры действий: `create`, `get`, `finish`.
   - Единый обработчик и маппер доменных ошибок `domainerror` в формат RFC 7807 (`api.Problem`).
   - Middleware: `Recover`, `Tracing`, `Logging`, `Metrics`, `Timeout`, `Idempotency`.
   - Порядок middleware строго фиксирован: `Recover -> Tracing -> Logging -> Metrics -> router`.

5. **Инфраструктура и Observability (`internal/infra`)**:
   - `internal/infra/telemetry`: настройка OpenTelemetry SDK (OTLP экспортеры трейсов и метрик, W3C Trace Context).
   - Сбор 5 обязательных метрик: `http.server.request.duration`, `http.server.active_requests`, `db.client.operation.duration`, `tripgo.trips.created`, `tripgo.trips.completed`.
   - `slog` JSON в stdout с автоматической корреляцией трейсов (`trace_id`, `span_id`).
   - Трейсинг базы данных через `otelpgx`.

6. **Контейнер зависимостей (`internal/container`)**:
   - Ручное внедрение зависимостей (manual DI) без использования сторонних DI-фреймворков.

## Опрос устаревших поездок

Компонент фонового опроса предназначен для асинхронного запроса координат у водителей, чьи устройства давно не присылали точек.

### Архитектурная схема

```text
[PostgreSQL] (выборка активных поездок порциями через keyset pagination)
      │
      ▼
   [Сканер] (одна горутина, time.Ticker: POSITION_CHECK_INTERVAL)
      │
      ├── (дедупликация + вытеснение свежих задач при переполнении)
      ▼
   [Очередь] (приоритетная очередь min-heap на базе container/heap)
      │
      ├── (вычитка задач начиная с самых давно молчащих)
      ▼
 [Worker Pool] (POSITION_WORKERS горутин)
      │
      ├── (проверка отмены: если координата пришла, задача дропается)
      ▼
 [Push Gateway] ──HTTP POST /api/v1/push──> [Push Service]
```

### Параметры конфигурации

| Переменная | Описание | Значение по умолчанию |
|---|---|---|
| `POSITION_CHECK_INTERVAL` | Интервал тика сканера для опроса устаревших поездок | `30s` |
| `POSITION_STALE_AFTER` | Время молчания, после которого поездка считается устаревшей | `60s` |
| `POSITION_WORKERS` | Число параллельных воркеров-обработчиков очереди | `4` |
| `POSITION_QUEUE_SIZE` | Размер буфера очереди задач | `100` |
| `POSITION_SCAN_BATCH_SIZE` | Размер порции при батчевом чтении выборки из БД | `100` |
| `PUSH_HTTP_URL` | Базовый URL сервиса Push-уведомлений | генерируется tripgoctl |
| `PUSH_REQUEST_TIMEOUT` | Таймаут на выполнение одного HTTP-запроса push | `1s` |

### Поведение при исчерпании очереди

Сканер никогда не блокируется на записи в очередь:
1. Если буфер очереди заполнен (`len == cap`), проверяется приоритет: если новая задача молчит дольше самой свежей задачи в очереди, она вытесняет её, а вытесненная помечается как `dropped`. Если новая задача свежее всех в очереди — дропается она сама.
2. При выпадении задачи инкрементируется метрика `tripgo.stale_checks{result="dropped"}` и пишется структурированный лог `Warn`.
3. Первый `dropped` на тике сигнализирует сканеру о перегрузке очереди (backpressure) и останавливает дальнейшие запросы батчей к БД на текущем тике. Поездка при этом не теряется: она по-прежнему остаётся без свежих координат в БД и будет отобрана на следующем тике.

### Реализованные задания со звёздочкой

#### 1. Выборка батчами (Keyset Pagination)
- Вместо одного тяжёлого запроса на всю таблицу сканер читает подходящие поездки порциями `POSITION_SCAN_BATCH_SIZE` (по умолчанию `100`).
- Пагинация реализована без использования `OFFSET` по составному ключу `(coalesce(last_position_at, started_at), id)`. Добавление `id` гарантирует строгий порядок: при совпадении времени у нескольких поездок ни одна строка не теряется и не вычитывается повторно.
- Под запрос создан составной индекс `trip_survey_index` на `((CASE WHEN last_position_at IS NOT NULL THEN last_position_at ELSE started_at END) ASC, id ASC) WHERE status = 'active'`, дающий чистый `Index Scan`.
- Сканер прерывает вычитку последующих батчей на тике при получении первого `dropped` или при возврате порции меньше `POSITION_SCAN_BATCH_SIZE`.

#### 2. Приоритетная очередь с вытеснением
- Реализована собственная потокобезопасная приоритетная очередь на базе `container/heap` (min-heap по эффективному времени последней точки: `last_position_at`, а при его отсутствии — `started_at`).
- Воркер всегда забирает первой ту поездку, которая молчит дольше всех, независимо от того, на каком тике она поступила в очередь. При одинаковом времени сохраняется порядок поступления (`seq`).
- **Вытеснение**: при полной очереди более старая поездка вытесняет самую свежую из очереди (вытесненная учитывается как `dropped` с логом `Warn`), а если новая поездка свежее всех — дропается она сама.
- Ожидание воркеров в `Dequeue` синхронизировано без использования `time.Sleep`, корректно завершается по отмене контекста и не оставляет горутин.

## Решения

- Транзакции используют `Read Committed`: уникальные ограничения и блокировка
  строки обеспечивают нужную конкурентную корректность без более строгой
  изоляции. Менеджер кладёт `pgx.Tx` в `context`, откатывает её при ошибке или
  панике и переиспользует при вложенном `Do`.
- Две активные поездки одного водителя запрещены частичным уникальным индексом
  `trips_one_active_per_driver_idx`. Завершение сериализуется через
  `SELECT ... FOR UPDATE`.
- `Idempotency-Key` хранится 24 часа по умолчанию. Middleware берёт
  транзакционную advisory lock, сравнивает SHA-256 тела и сохраняет HTTP-ответ в
  той же транзакции, что поездку и историю. Повтор возвращает ту же поездку с
  `200`, другое тело — `409 idempotency_conflict`.
