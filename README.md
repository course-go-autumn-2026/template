# Trip Service

Это сервис для первой лабораторной по Go. Он умеет создавать поездку, получать
её по ID и завершать. Данные хранятся в PostgreSQL.

## Что нужно для запуска

- Go 1.25+
- Docker
- GNU Make
- `tripgoctl`

`oapi-codegen` и `goose` уже добавлены в `go.mod`, отдельно устанавливать их не
нужно.

## Запуск

```bash
go mod download
tripgoctl cluster start
tripgoctl environment start
tripgoctl connect
make generate
make migrate
make run
```

`tripgoctl cluster start` достаточно выполнить один раз на компьютере. Команда
`tripgoctl environment start` поднимает PostgreSQL и создаёт `.env`. Файлы
`.env` и `.tripgo/` локальные, в Git они не добавляются.

По умолчанию после запуска сервис доступен на `localhost:8080`.

Проверить его можно так:

```bash
curl -i http://localhost:8080/health
curl -i http://localhost:8080/ready
```

`/health` проверяет, что приложение работает. `/ready` дополнительно проверяет
подключение к PostgreSQL и вернёт `503`, если база недоступна.

## Ручки

| Метод | Путь | Что делает |
|---|---|---|
| `POST` | `/api/v1/trips` | создаёт поездку |
| `GET` | `/api/v1/trips/{tripId}` | возвращает поездку |
| `POST` | `/api/v1/trips/{tripId}/finish` | завершает поездку |
| `GET` | `/health` | проверяет приложение |
| `GET` | `/ready` | проверяет приложение и базу |

Ошибки бизнес-ручек возвращаются в формате `application/problem+json`.

## Команды Makefile

```bash
make generate        # пересоздать код из OpenAPI
make migrate         # применить миграции
make migrate-down    # откатить последнюю миграцию
make migrate-status  # показать состояние миграций
make run             # запустить сервис
```

Сгенерированный файл лежит в `api/api.gen.go`. Его не нужно менять руками.
`make generate` берёт контракт из `contracts/openapi` и генерирует только ручки
первой лабораторной.

## Переменные окружения

Все настройки сервис получает из окружения. Локальные значения лежат в `.env`,
а пример со всеми переменными — в `.env.example`.

| Переменная | Для чего нужна |
|---|---|
| `HTTP_ADDR` | адрес HTTP-сервера |
| `HTTP_READ_TIMEOUT` | таймаут чтения запроса |
| `HTTP_READ_HEADER_TIMEOUT` | таймаут чтения заголовков |
| `HTTP_WRITE_TIMEOUT` | таймаут записи ответа |
| `HTTP_IDLE_TIMEOUT` | таймаут keep-alive соединения |
| `LOG_LEVEL` | уровень логирования |
| `SHUTDOWN_TIMEOUT` | время на корректную остановку |
| `IDEMPOTENCY_TTL` | срок действия ключа идемпотентности |
| `DATABASE_URL` | строка подключения к PostgreSQL |
| `DATABASE_MAX_CONNS` | максимальное количество соединений |
| `DATABASE_MIN_CONNS` | минимальное количество соединений |
| `DATABASE_MAX_CONN_LIFETIME` | время жизни соединения |
| `DATABASE_CONNECT_TIMEOUT` | таймаут подключения к базе |
| `DATABASE_QUERY_TIMEOUT` | таймаут запросов к базе |

Переменных с HTTP-таймаутами и `IDEMPOTENCY_TTL` пока нет в `.env`, который
создаёт `tripgoctl`, поэтому для локального запуска `Makefile` задаёт им
значения по умолчанию.

## Что сделано

- HTTP-сервер на `net/http` и `chi`
- создание, получение и завершение поездки
- проверка входного JSON по OpenAPI-контракту
- миграции для `trips` и `trip_status_history`
- работа с PostgreSQL через `pgxpool` и `squirrel`
- транзакция для записи поездки и истории статуса
- `/health`, `/ready`, таймауты и graceful shutdown
- защита от двух активных поездок одного водителя
- защита от двух одновременных завершений одной поездки
- идемпотентное создание поездки по заголовку `Idempotency-Key`

## Решения

### Транзакции

Для транзакций я выбрал `Read Committed`. Его здесь хватает: две активные
поездки защищены индексом в базе, а завершение — условием в `UPDATE`. Более
строгий уровень добавил бы ошибки сериализации, которые пришлось бы отдельно
обрабатывать.

Транзакции запускаются через `TxManager.Do`. Он кладёт `pgx.Tx` в `context`.
Репозиторий проверяет контекст: если там есть транзакция, запрос выполняется
через неё, иначе через обычный пул. Сервисный слой при этом ничего не знает о
`pgx`.

Если функция внутри `Do` завершилась успешно, выполняется `COMMIT`. При ошибке
или панике выполняется `ROLLBACK`, после чего ошибка или паника передаётся выше.
Вложенный вызов `Do` использует уже открытую транзакцию.

### Конкурентные запросы

Чтобы у водителя не появилось две активные поездки, в PostgreSQL добавлен
частичный уникальный индекс по `driver_id` для статуса `active`. Ошибка
PostgreSQL `23505` переводится в `409 driver_busy`.

Завершение сделано одним запросом с условием
`UPDATE ... WHERE status = 'active'`. При двух одновременных запросах один
завершит поездку, а второй получит `409 trip_completed`.

### Идемпотентность

`POST /api/v1/trips` можно отправить с заголовком `Idempotency-Key`. Ключ должен
быть UUID.

| Запрос | Ответ |
|---|---|
| первый запрос с новым ключом | `201`, создаётся поездка |
| тот же ключ и те же данные | `200`, возвращается та же поездка |
| тот же ключ, но другие данные | `409 idempotency_conflict` |
| запрос без ключа | обычное создание с ответом `201` |

Ключ действует 24 часа. Срок можно поменять через `IDEMPOTENCY_TTL`. После
истечения срока этот ключ снова считается новым. Старая поездка не удаляется,
поэтому для ещё активного водителя обычное правило `driver_busy` продолжает
работать.

Для сравнения запросов сохраняется SHA-256 fingerprint всех полей тела. Он
считается уже после разбора JSON, поэтому пробелы и порядок полей не влияют на
результат. При повторе сервис читает поездку из базы и возвращает её текущее
состояние.

Ключ, fingerprint и ID поездки записываются в PostgreSQL в той же транзакции,
что поездка и первая запись истории. Уникальный индекс по ключу не даёт двум
одновременным запросам создать две поездки.
